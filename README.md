# StackBridge Invites

_A product of [StackBridge Labs](https://www.stackbridgelab.com) — built by developers for the world._

**Invite → Experience → Remember.** A multi-tenant SaaS for premium digital wedding invitations, sold at
₹2,000–₹10,000 per wedding. One invitation engine, three packages (Essential / Signature / Luxury) that differ
only by *feature entitlements*, and a bilingual guest experience (English + Malayalam, or any local language
Super Admin chooses when creating the wedding).

No AI features anywhere. Everything runs on free/open-source software; the only paid dependency you may want is
an email provider.

---

## Quick start (no accounts, no Docker)

```bash
npm install
cp .env.example .env.local     # optional for local use
npm run setup                  # migrates the embedded database and seeds demo weddings
npm run dev                    # http://localhost:3000
```

Development uses **PGlite** (a real PostgreSQL compiled to WebAssembly) stored in `.data/pg`, and local disk for
media in `storage/`. Production uses PostgreSQL (Supabase) and S3-compatible storage (Cloudflare R2) — the same
migrations and the same code.

## What is in the box

**Super Admin studio** (`/admin`): dashboard with an "needs your attention" list; weddings (search, filter,
duplicate, archive, publish/unpublish); a **16-step creation wizard** with autosave, undo/redo and live preview
(including choosing the local language); a **structured visual editor** (sortable sections, layouts, wording,
per-section visibility, theme and opening controls, checkpoints, publish — no free-form CSS/HTML/JS); templates
and themes libraries (duplicate, recolour, retire); media library with moderation; packages with editable prices
and feature sets; clients (one-time sign-in links, pause access); orders ledger (including the first-five
**FREE_PORTFOLIO** class); guests search across weddings; analytics; custom domains; notification outbox; audit
& system logs; settings and platform health.

**Client dashboard** (`/client`, Signature/Luxury only): only what Super Admin has approved — RSVPs, guests, wishes,
photos, gallery, check-in, live day, games, time capsule, memories. Clients can never edit design code and can only
publish updates to an invitation Super Admin has already launched.

**Guest experience** (`/invite/{slug}` and `/invite/{slug}/{secureToken}`): opening gate (envelope, seal, cinematic,
swipe, curtains), countdown, couple, story, events with per-guest visibility, venue and travel, gallery, dress code,
menu, RSVP, guestbook, video/voice wishes, photo uploads (moderated), live updates, QR guest pass, games, time
capsule, post-wedding memory book and anniversary mode. No account is ever required.

**The invitation experience** (the cinematic layer — see [docs/IMAGES.md](docs/IMAGES.md) for photography):

* **Opening scene** — a full-viewport photograph of the couple (a portrait for phones, an optional landscape
  version for desktops, both cropped on the faces' focal point), a scrim that is deepest behind the words, then the
  invitation line, the names in a display serif, *are getting married*, the date as `12 • 12 • 2026`, and a scroll cue.
* **Opening celebration** — played once when the invitation opens: a few dozen marigold, rose and jasmine petals for a
  Hindu wedding, gold confetti fired from both edges for everything else. Driven by `doc.eventType`
  (`hindu_wedding`, `christian_wedding`, `muslim_wedding`, `engagement`, `reception`, `birthday`,
  `anniversary`), overridable per wedding, skipped for reduced motion, one canvas that removes itself.
* **The walking couple** — two small hand-drawn figures (lehenga & sherwani, kasavu & mundu, or gown & suit) start in
  the bottom corners and walk towards each other as the guest scrolls — a pure function of scroll progress, not a
  one-off entrance — and stand hand in hand, with a glow and one small heart, in the final section.
* **A story, in order** — the photograph → *Our story* (four opening lines beside a portrait) → *The beginning*
  (dated milestones that draw a line down the page) → an elegant rolling countdown (*Today is the day ♥*) → the couple →
  each day as a magazine spread (date numerals, venue, address, Google Maps) → the *ceremonies* (the family's own list;
  nothing assumes a particular ritual) → the families set as typography → the venue → editorial gallery spreads with a
  swipe/keyboard lightbox → the *wedding film* (hidden when there is none) → RSVP → WhatsApp.
* **Music** — a floating ♪ control with three honest states (off / playing / paused). Audio never starts by itself.
* **WhatsApp** — a quiet "Chat with us on WhatsApp" pill under the RSVP, in the contacts and at the very end.

**Lifecycle** — DRAFT → PREVIEW → PUBLISHED → LIVE_EVENT → POST_EVENT → MEMORY → ANNIVERSARY — follows the wedding
date and timezone automatically; publishing snapshots a version you can roll back to.

Every one of the 55 entitlements (grouping the 90 approved capabilities) is listed in
[docs/FEATURES.md](docs/FEATURES.md) with the package that includes it by default.

## Architecture

```
src/
  db/            Drizzle schema (multi-tenant Postgres) and the dual PGlite / postgres-js client
  domain/        Business rules. Services take an Actor; nothing here knows about HTTP or React
    auth/        sessions, magic links, requireWeddingAccess (the single tenant + entitlement gate)
    packages/    feature catalogue, entitlement resolution, package pricing
    doc/         InvitationDoc (Zod) — the one source of truth for an invitation's content
    design/      theme tokens, themes, structural templates
    wedding/     drafts, publishing, versions, lifecycle, server-side visibility filtering
    guests/ participation/ live/ games/ memory/ media/ analytics/ notify/ platform/
  invitation/    The guest-facing engine: sections, opening gate, i18n, theming, motion
  components/    Studio UI: shell, wizard, editor, workspace pages, media library
  app/           Next.js routes and server actions (thin wrappers over domain services)
  proxy.ts       Custom-domain routing
drizzle/         SQL migrations      scripts/  seed, migrate, reset, dev tools      tests/  Vitest suites
```

Key ideas:

* **One engine.** Template + Theme + Data + Features + Media + Sections + Guest context. Packages are rows of
  feature keys in `wedding_packages`; a wedding may override single features. Sections declare the feature they
  need, and the server refuses (not just hides) anything the package does not include.
* **Tenant isolation.** Every service call goes through `requireWeddingAccess(actor, weddingId)`; there is a test
  suite that attacks it (client A reading client B, unauthenticated calls, disabled users).
* **Privacy by construction.** Event, venue and section visibility is decided on the server before data reaches the
  browser; phone numbers, emails and notes never enter the public payload; guest tokens are 256-bit random values;
  analytics use a random per-browser id (no IP, no fingerprint).
* **Content is data.** Editors change a validated document, never markup or scripts. Uploads are byte-sniffed
  (no SVG/HTML/HEIC), re-encoded to WebP with EXIF/GPS removed, and served through an access-controlled route.
* **Realtime without infrastructure.** One shared, visibility-aware poller per resource (swappable for Supabase
  Realtime without touching sections).
* **Local language.** Content is stored as `{ en, ml, … }`. English and Malayalam interface strings ship complete;
  other languages can be added per wedding from the wedding's language settings with its own wording. Malayalam
  typography rules (no tracking/uppercase, taller line-height, Noto Serif Malayalam) are built in.

## Configuration

Copy `.env.example`. Nothing is required locally.

| Variable | Purpose |
|---|---|
| `APP_URL` | Public origin — used in share links, QR codes and OG tags |
| `APP_SECRET` | 24+ random characters (required in production) |
| `DATABASE_URL` | PostgreSQL connection string. Empty = embedded PGlite (dev only) |
| `STORAGE_DRIVER` | `local` or `s3` (Cloudflare R2 or any S3-compatible bucket) |
| `S3_ENDPOINT` `S3_REGION` `S3_BUCKET` `S3_ACCESS_KEY_ID` `S3_SECRET_ACCESS_KEY` `S3_PUBLIC_BASE_URL` | Object storage |
| `RESEND_API_KEY` `EMAIL_FROM` | Optional email. Without a key, messages are recorded in the outbox |
| `CRON_SECRET` | Protects `/api/cron` (Vercel Cron sends it automatically) |
| `SEED_ADMIN_EMAIL` `SEED_ADMIN_PASSWORD` `SEED_ADMIN_NAME` `SEED_DEMO` | Seeding; `SEED_DEMO=false` creates only the admin and packages |

## Deploying (Vercel + Supabase + Cloudflare R2)

1. **Supabase**: create a project, copy the *pooled* connection string into `DATABASE_URL`.
2. **Cloudflare R2**: create a bucket and an API token; set the `S3_*` variables and `STORAGE_DRIVER=s3`.
   (Vercel has no permanent disk, so `local` storage will not work there.)
3. **Vercel**: import the repo, set `APP_URL`, `APP_SECRET`, `CRON_SECRET` and the variables above.
4. From your machine, against the production `DATABASE_URL`:
   `npm run db:migrate && SEED_DEMO=false SEED_ADMIN_PASSWORD='a-long-unique-password' NODE_ENV=production npm run db:seed`
5. Sign in at `/login`, open **Settings** — *Platform health* tells you what is still unconfigured.
6. Custom domains: add the domain in Vercel, then in **Studio → Domains** connect it to a wedding and mark it
   verified once DNS resolves. `vercel.json` schedules the daily `/api/cron` job.

Health probe for uptime monitors: `GET /api/health`.

## Honest limitations

* **Existing deployments keep their old look until the library is refreshed.** Built-in templates and themes are inserted
  only when missing and packages keep the feature set stored in their row. After deploying a design release run
  `npm run library:refresh`: it updates built-in templates/themes that nobody has edited in the studio (versioned and
  audited) and reports — and leaves alone — any that were edited. Already-published invitations are snapshots and do not
  change; each wedding keeps its own section list, so only *new* weddings pick up a template change, while a draft
  picks up theme changes (fonts, colours) on its next preview. New document fields have safe defaults (Hindu wedding,
  petals, the walking couple on). `SEED_ONLY=ananya-and-arjun npm run db:seed` adds just the new showcase demo to an
  existing database.
* The stock demonstration photographs depict real people (see the credits file); they are for demos only.
* Payments are recorded by hand in **Orders**; there is no payment gateway.
* WhatsApp is **click-to-send** (`wa.me` links prepared per guest), not the WhatsApp Business API.
* Live updates use polling (6–30 s), not websockets — deliberate, for cost and simplicity.
* Only English and Malayalam interface strings ship complete; other local languages need per-wedding wording.
* Automated tests cover the domain layer (security, entitlements, RSVP, publishing, media, check-in, capsule,
  games). UI was verified visually with Playwright screenshots at phone, tablet and desktop widths; there is no
  automated browser test suite yet.
* Custom-domain DNS verification is a manual switch, not an automatic DNS check.

## Deploying to a single VPS (nginx + systemd + local PostgreSQL)

This is how the reference server runs it; templates are in `deploy/`.

1. Install Node 22, create a database and role (`createdb -O stackbridge_user stackbridge_invites`).
2. Copy the source to `/home/deploy/apps/stackbridge-invites`, then create `.env.production` from
   `deploy/env.production.example` (`chmod 600`; generate `APP_SECRET`, `CRON_SECRET` and a strong `SEED_ADMIN_PASSWORD`).
3. `npm ci && set -a && . ./.env.production && set +a && npx next build && npm run db:migrate && npm run db:seed`
4. `cp deploy/stackbridge-invites.service /etc/systemd/system/ && systemctl enable --now stackbridge-invites`
5. `cp deploy/nginx-stackbridge-invites.conf /etc/nginx/sites-available/stackbridge-invites`, symlink into `sites-enabled`,
   `nginx -t && systemctl reload nginx`, and open the port in the firewall. The nginx block must forward
   `Host $http_host` (with the port) or Next.js rejects sign-in as a cross-origin request.
6. Daily job: `30 2 * * * curl -fsS -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:8104/api/cron`.

**Update:** upload the new source, `npm ci`, rebuild, `systemctl restart stackbridge-invites`, and `npm run db:migrate` if the schema changed.

**Switch media to AWS S3:** create a private bucket and an IAM user limited to it, set `STORAGE_DRIVER=s3`,
`S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (leave `S3_ENDPOINT` empty for AWS), run
`npm run storage:sync` once to copy existing files, then restart the service.

**Go public with HTTPS:** point a domain at the server, add a second nginx `server_name`, run certbot, set
`APP_URL=https://your.domain`, restart. Cookies become `Secure` automatically.
